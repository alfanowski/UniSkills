# Architecture

## 1. Layers

```text
┌──────────────────────────────────────────────────────────────┐
│ Packs            ordered playbooks over existing skills      │
├──────────────────────────────────────────────────────────────┤
│ Skills           one capability each, standalone bundles     │
├──────────────────────────────────────────────────────────────┤
│ Standard         method, evidence, depth, output, safety     │
└──────────────────────────────────────────────────────────────┘
```

The arrows point downward only. A skill may reference the standard conceptually, but must not depend on
repository files at runtime — a single installed skill has to work alone.

## 2. Why skills are standalone, and what that costs

The Agent Skills format loads one directory. If a skill's instructions say "see `../../docs/method.md`",
that link breaks the moment somebody installs only that skill.

Three options were considered:

| Option | Cost | Problem |
| --- | --- | --- |
| Every skill imports a shared file by path | No duplication | Breaks single-skill install; wrong for the format |
| Generate bundles from templates at release time | Build step, generated files in git | Edits land in generated files; reviews get noisy |
| Embed a compact contract in every skill, keep depth in references | ~110 duplicated words per skill | Accepted |

The third option wins because the duplicated part is small, stable, and machine-checked.
`templates/operating-contract.md` is the canonical text; `tools/validate_skills.py` fails if any skill's
embedded copy drifts. Drift is therefore impossible to merge, which removes the usual argument against
duplication.

What is **not** duplicated: the full method, evidence taxonomy, depth rationale, domain checklists. Those
live in `docs/` as the canonical reference and in per-skill `references/` for agents.

## 3. Progressive disclosure budget

| Layer | Loaded when | Budget |
| --- | --- | --- |
| `name` + `description` | Always, for every installed skill | ≤ 1024 chars each |
| `SKILL.md` body | On activation | ≤ 500 lines (hard fail at 700) |
| `references/*.md` | Explicitly, per workflow step | No hard limit; one level deep |
| `scripts/` | Executed, not read | Deterministic, documented |

Rules enforced by the validator:

- Required sections in a fixed order, so an agent can navigate by heading.
- Every reference file must be linked from `SKILL.md`, and no reference may link to another reference.
  This prevents the "partially read nested document" failure described in the Anthropic authoring guide.
- Depth profiles must be a table covering all four profiles.

## 4. Catalog as source of truth

`catalog/skills.yaml` is authoritative. `catalog/SKILL_CATALOG.md` and `catalog/ROADMAP.md` are
generated by `tools/render_catalog.py`; CI runs it with `--check` and fails on drift. This kills the
classic failure where the README advertises ten skills and three exist.

Invariants:

- A `flagship` entry must have a directory, a `SKILL.md`, an eval file, and a maturity that matches its
  frontmatter.
- A `planned` or `deferred` entry must **not** have a directory. Empty directories are forbidden because
  they read as shipped capability.
- Pack membership is bidirectional: the catalog and `catalog/packs.yaml` must agree.

## 5. Tooling

Everything is Python 3 standard library, no install step.

| Tool | Role | Why it exists |
| --- | --- | --- |
| `yamlmini.py` | YAML subset parser | PyYAML is not guaranteed in every environment; a hidden dependency would break the "clone and run" promise |
| `lintlib.py` | Shared diagnostics, fence-aware markdown scanning | One place for line-accurate errors |
| `validate_skills.py` | Frontmatter, sections, contract, links, length, evals | The authoring standard, executable |
| `validate_catalog.py` | Catalog, packs, filesystem consistency | Prevents phantom skills |
| `check_links.py` | Relative links in markdown | Offline, deterministic |
| `check_secrets.py` | Secret patterns, personal paths | Cheap guard against the worst mistake |
| `eval_runner.py` | Case schema + prompt assembly | Makes evals runnable without pretending to run them |
| `render_catalog.py` | Catalog views | No manual drift |

### The parser decision

Writing a YAML parser is normally a bad trade. Here it is justified because the alternative is a hard
dependency for a project whose entire value proposition includes "copy this directory and it works".
The subset is small, explicitly documented, and **rejects** unsupported syntax instead of guessing.

Verification: `tools/tests/test_yamlmini.py` includes a differential test that parses every `.yaml` file
in the repository with both `yamlmini` and PyYAML (when installed) and asserts identical trees. PyYAML is
never required at runtime; it is only an oracle in the test suite.

## 6. Evaluation lab

Structure, not execution:

- `evals/cases/<skill>.yaml` — three or more cases per skill: a standard path, a boundary or adversarial
  path, and a false-positive guard.
- Each case declares `must` and `must_not` expectations and a rubric with at least three scored
  dimensions.
- `tools/eval_runner.py --check` validates the schema; `--prompt <id>` assembles a runnable prompt.

No model is called by the tooling. Claiming a pass rate without recorded runs would be exactly the kind
of fabricated metric this project exists to oppose. The methodology that a human or an external harness
should follow is in [evaluation-methodology.md](evaluation-methodology.md).

## 7. Composition rules

A pack is an ordered list of existing skills plus a document explaining:

- why that order;
- what each skill consumes and produces;
- what to do when one skill is enough;
- what the pack explicitly does not cover.

Packs never restate skill content. If two packs need the same paragraph, that paragraph belongs in a
skill.

## 8. Repository map

```text
README.md                 entry point, quick start, catalog summary
docs/                     vision, architecture, standards, safety, methodology
catalog/                  source of truth + generated views
skills/<name>/            installable bundles
packs/                    ordered playbooks
templates/                skill template, finding schema, output templates
tools/                    validators, parser, renderer, tests
evals/                    cases, rubrics, fixtures
examples/                 worked end-to-end examples with synthetic data
.github/                  CI and issue configuration
```

## 9. Rejected alternatives

| Alternative | Why rejected |
| --- | --- |
| One mega-skill with a routing table inside | Loads everything for every task; impossible to evaluate per capability |
| A plugin marketplace / installer in 0.1.0 | Requires writing to user config; needs dry-run, backup, and uninstall to be safe. Deferred until the skill set is stable |
| YAML frontmatter with custom required fields | Would break other Agent Skills clients; `metadata` carries our fields instead |
| JSON for the catalog | Worse for human review and diffs; the parser cost was acceptable |
| Generated skill bundles from a template engine | Build complexity and noisy diffs for a small deduplication win |
| Model-backed eval runner | Cost, API keys, and non-determinism; the schema and rubric are the durable part |

## 10. Known structural limits

- Descriptions are the only routing signal in most clients; a badly written description is invisible to
  the validator beyond basic shape checks.
- The validator checks structure, not judgment. A well-formed but mediocre skill passes.
- Cross-skill consistency is manual: nothing detects two skills giving contradictory advice.
- The catalog covers more than is implemented; that is intentional and labeled, but it is still a
  surface for over-claiming.
