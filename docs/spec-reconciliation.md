# Specification Reconciliation

The project started from an external master specification (`UNISKILLS_MASTER_PROJECT_SPEC.md`) plus a
clarifying mandate. Where the two disagreed, the mandate won. This page records every material divergence
between the starting specification and what was built, so a reader can see the change rather than infer it.

No copy of the master specification is stored in this repository; it is not part of the deliverable.

## 1. Flagship set

| Specification | Delivered | Reason |
| --- | --- | --- |
| 12 flagship skills, including `assembly-machine-code-analysis` | 12 flagship skills, that one replaced by `evidence-validation` | The mandate defines "reason like assembly analysis" as a resolution analogy, not a product requirement. A standalone assembly skill would duplicate `reverse-engineering`'s evidence model. |
| `assembly-machine-code-analysis` as a first-class capability | Instruction-level reference inside `reverse-engineering` | ISA, ABI, stack frames, signedness, and decompiler artifacts are only useful when a question requires them. Keeping them on-demand avoids loading 100+ lines of low-level detail for a code review. |
| Catalog entry optional | Entry kept as `status: deferred` with the reason in `summary` | Visible so nobody re-adds it by accident, and honest about the decision. |

Net effect: twelve skills, one swapped for the capability every other skill depends on.

## 2. Evaluation layout

| Specification | Delivered | Reason |
| --- | --- | --- |
| `evals/manifest.yaml` | `evals/cases/<skill>.yaml`, one file per skill | A single manifest duplicates the skill list and drifts. Per-skill files are discovered, validated, and diffed independently. `tools/eval_runner.py` reconstructs the global index. |
| `evals/rubrics/` directory | `evals/rubrics/grading-rubric.md` | One shared rubric with per-dimension definitions; per-case rubrics already live inside each case. |
| `evals/fixtures/` with samples | Documented convention, no fixtures yet | Every current case carries its own context inline. Adding fixtures without a case that needs them would be scaffolding. |

## 3. Pack layout

| Specification | Delivered | Reason |
| --- | --- | --- |
| `packs/<name>/` directories | `packs/<name>.md` plus `catalog/packs.yaml` | A pack is a document plus a membership list. A directory would imply installable content, which would duplicate skills. |
| Packs that include planned skills (threat modeling, test strategy, binary triage) | Six packs built only from shipped skills | A pack that references a nonexistent skill is a broken promise. The reduced packs say what they would include later. |

## 4. Catalog

| Specification | Delivered | Reason |
| --- | --- | --- |
| `catalog/roadmap.md` | `catalog/ROADMAP.md` (generated) | Generated from `skills.yaml` so it cannot drift; capitalized to match the other generated view. |
| Markdown catalog maintained by hand | Generated by `tools/render_catalog.py`, checked in CI | Manual tables drift from reality within one release. |
| Full field set in the markdown view | Full field set in YAML; grouped view in markdown | The YAML is the contract; the view is for humans and stays readable. |

## 5. Tooling

| Specification | Delivered | Reason |
| --- | --- | --- |
| Use PyYAML if justified | In-repo subset parser, zero dependencies | A hidden dependency breaks "clone and run". The subset is documented, strict, and differential-tested against PyYAML. |
| `validate_skills.py`, `validate_catalog.py`, `lint_skill_links.py` | `validate_skills.py`, `validate_catalog.py`, `check_links.py`, `check_secrets.py`, plus a renderer and eval checker | Link and secret checks are separate concerns with different failure modes and different scopes. |
| Eval runner "only if robustly implementable" | Schema validator plus prompt assembler, no model calls | Execution needs credentials, budget, and determinism controls that the repository does not have. |

## 6. Content policy

| Specification | Delivered | Reason |
| --- | --- | --- |
| Shared standards possibly built into skills via a build step | A ~110-word contract embedded verbatim and drift-checked | No build step, no generated files in review, still impossible to diverge silently. |
| "Assembly, ABI, compilers, binary analysis" as a distinctive area | One `reverse-engineering` skill with a low-level reference | Distinctiveness is claimed through method and evidence, not through catalog breadth. |
| Comprehensive taxonomy as skills | Comprehensive taxonomy as catalog entries, 32 planned | The mandate explicitly prefers few deep skills to many shallow files. |

## 7. What did not change

- The evidence vocabulary (`VERIFIED` … `N/A`) and the "no fabricated results" rule.
- The four depth profiles and the risk-based escalation list.
- The safety posture: read-only default, authorization gates, untrusted content is data.
- The requirement that every skill be installable alone.
- The refusal to push, tag, release, or publish without authorization.

## 8. Where the mandate was silent

Two choices were made and recorded rather than escalated:

1. **MIT license**, flagged as pending owner confirmation in
   [`decision-log.md`](decision-log.md#d1--license-mit).
2. **Catalog size** (46 entries) exposing the planned roadmap publicly. If that is undesirable, removing
   the `planned` rows is a mechanical edit to one YAML file, followed by the renderer.
